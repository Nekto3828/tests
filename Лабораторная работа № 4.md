# Лабораторная работа № 4

**Объединение IP-АТС, межстанционная маршрутизация и работа через NAT**

## 1. Цель работы

Цель работы — построить взаимодействующую систему из трёх серверов Asterisk 22.11.0, организовать межстанционные вызовы по PJSIP, сквозную маршрутизацию с резервным направлением и исследовать прохождение SIP- и RTP-трафика через NAT.

В результате студент должен продемонстрировать звонки между абонентами разных станций, объяснить выбор маршрута и причину отказа, диагностировать одностороннюю слышимость по SIP/SDP/RTP и устранить её без публикации учебной АТС в Интернет.

## 2. Теоретические сведения

### 2.1. Межстанционный SIP-транк

Транк — логическая связь между телефонными станциями, используемая для передачи вызовов. В [PJSIP](https://docs.asterisk.org/Configuration/Channel-Drivers/SIP/Configuring-res_pjsip/) соединение описывают объекты endpoint (параметры канала и контекст входящих вызовов), aor (адрес удалённой станции), identify (сопоставление входящего SIP-запроса с endpoint по IP-адресу). Для транка по фиксированному адресу регистрация не обязательна; регистрация и аутентификация — отдельные механизмы.

При передаче вызова Asterisk создаёт отдельное SIP-плечо к другой станции. В диалплане вызываемый номер сохраняется или преобразуется согласно единому плану нумерации. Контексты входящих транков должны разрешать только предназначенные для них диапазоны: использование внутреннего контекста без ограничений создаёт риск несанкционированной маршрутизации.

### 2.2. Межстанционная маршрутизация и резерв

В единой нумерации первые две цифры четырёхзначного номера обозначают станцию, две последние — абонента. АТС A использует код 10+v (v — номер варианта 1–30), станции B и C — коды 91 и 92. Например, для варианта 1 абонент A имеет номер 1101, B — 9101, C — 9201.

Топология «цепочка» A–B–C требует транзита вызова A→C через B. В «треугольнике» A–B–C–A можно предусмотреть резервный путь A→B→C при отказе прямого A→C. Переключение по DIALSTATUS должно отличать сетевую недоступность транка (например, CHANUNAVAIL или CONGESTION в зависимости от причины) от состояний занятого или неотвечающего абонента: BUSY и NOANSWER сами по себе не означают отказ линии.

### 2.3. NAT, SDP и RTP

NAT изменяет IP-адрес и, возможно, порт пакетов при прохождении маршрутизатора. SIP содержит адреса сигнализации в заголовках, а [SDP](https://www.rfc-editor.org/info/rfc8866/) описывает адрес и порт получения медиапотока (поля c= и m=). Если адрес в SDP недоступен удалённой стороне, вызов может установиться при отсутствии звука в одном направлении.

Для клиента за NAT проверяются настройки endpoint rtp_symmetric, force_rport, rewrite_contact и direct_media=no. Они выполняют разные функции: симметричный RTP направляется к фактическому источнику принятых RTP-пакетов; force_rport влияет на SIP-ответы; rewrite_contact корректирует адрес последующих запросов; direct_media=no сохраняет Asterisk в медиатракте. Настройки external_* относятся к случаю, когда за NAT находится сам сервер Asterisk, и не должны вводиться автоматически.

Диагностика требует сопоставлять SIP, SDP и фактический RTP на каждом плече, а не только проверять сообщение 200 OK или успешную регистрацию.

## 3. Исходные условия

Используйте настроенную в предыдущих работах ВМ ast-a (Ubuntu Server 24.04 LTS, Asterisk 22.11.0, PJSIP). Перед клонированием сохраните снимок состояния. Создайте ВМ ast-b и ast-c; после полного клонирования замените имена узлов, machine-id, адреса сетевых адаптеров и, при необходимости, SSH host keys. Одновременный запуск клонов с совпадающими адресами запрещён.

Внутренняя сеть VirtualBox — voip-internal; у каждой ВМ отдельный адаптер Internal Network. В учебной внутренней подсети 10.77.v.0/24 используйте адреса A=10.77.v.10, B=10.77.v.20, C=10.77.v.30. У ast-a сохраняется Host-Only 192.168.56.(v+20)/24 для административного доступа. NAT-адаптер, применённый в ЛР № 1 для загрузки пакетов, не является частью основной лабораторной сети.

На каждой АТС должен работать хотя бы один локальный PJSIP-абонент с номером по плану нумерации; на A сохраняются абоненты предыдущих работ. Задействуйте только учебные изолированные сети и собственные тестовые учётные данные. Перед изменением конфигураций сохраните резервные копии pjsip.conf и extensions.conf внутри ВМ.

*Пример 1 — исходная проверка каждой АТС (Bash)*

```bash
hostnamectl --static
ip -br address
sudo asterisk -rx 'core show version'
sudo asterisk -rx 'pjsip show endpoints'
sudo asterisk -rx 'dialplan show'
```

## 4. Практическая часть

### 4.1. Соединение двух АТС посредством PJSIP

Проверьте IP-связность A↔B, существование отдельных локальных абонентов и отсутствие пересечений их номеров. Для начала используйте фиксированные IP-адреса транков без регистрации. Выделите на обеих сторонах отдельный контекст приёма транковых вызовов; не передавайте удалённым станциям права доступа к административным или платным направлениям.

Ниже показан учебный фрагмент на A для удалённой B. Он предполагает уже существующий UDP transport, настроенный в ЛР № 2. Аналогично создайте на B объект для A, заменив IP и имя. Укажите действительный transport при отличии его имени.

*Пример 2 — фрагмент pjsip.conf на АТС A*

```text
[trunk-b]
type=endpoint
transport=transport-udp
context=from-b
disallow=all
allow=alaw
aors=trunk-b
direct_media=no
[trunk-b]
type=aor
contact=sip:10.77.v.20:5060
qualify_frequency=30
[trunk-b-identify]
type=identify
endpoint=trunk-b
match=10.77.v.20
```

Запись 10.77.v.20 в примере обозначает адрес своего варианта: вместо v впишите десятичное число 1–30. После внесения изменений примените конфигурацию и убедитесь, что endpoint и AoR определены. Состояние qualify показывает доступность контакта, но не доказывает успешность разговора.

*Пример 3 — проверка PJSIP (Bash)*

```bash
sudo asterisk -rx 'pjsip reload'
sudo asterisk -rx 'pjsip show endpoint trunk-b'
sudo asterisk -rx 'pjsip show aor trunk-b'
```

Добавьте на A маршрут вызовов 91XX к B, а на B — маршрут кодов A к A. Для набора через статический AoR применяйте форму Dial(PJSIP/${EXTEN}@trunk-b,30). Для входящего транка B создайте контекст from-b с проверкой допустимых локальных номеров.

*Пример 4 — исходящий маршрут A→B в extensions.conf*

```text
[internal]
exten => _91XX,1,Dial(PJSIP/${EXTEN}@trunk-b,30)
 same => n,Hangup()
```

Фрагмент является только одним маршрутом; не дублируйте существующий [internal] вместо добавления правил в действующий контекст. Совершите звонки в обе стороны. При необходимости включите SIP logger на время диагностики и затем отключите.

### 4.2. Единая нумерация, транзит и резервирование

Присвойте B и C номера 91XX и 92XX. Создайте межстанционный транк B↔C. Постройте маршрутизацию A→B→C и обратную C→B→A; в каждом входящем транковом контексте явно ограничьте допустимые направления и число переходов. Выполните вызов A→C и объясните, через какие станции проходят два SIP-плеча.

Затем реализуйте топологию индивидуального варианта. Для «треугольника» предусмотрите прямой A↔C и транзитный резерв A→B→C. Для «цепочки» резервируйте доступность на уровне сценария обработки ошибки (без выдуманного второго физического пути): проигрывание служебного сообщения или завершение вызова с корректным признаком причины.

*Пример 5 — принцип ветвления по результату Dial()*

```text
exten => _92XX,1,Dial(PJSIP/${EXTEN}@trunk-c,20)
 same => n,GotoIf($["${DIALSTATUS}"="CHANUNAVAIL"]?backup)
 same => n,GotoIf($["${DIALSTATUS}"="CONGESTION"]?backup)
 same => n,Hangup()
 same => n(backup),NoOp(Primary path unavailable)
 same => n,Hangup()
```

Это демонстрация проверки статуса, не готовый резерв: в ветке backup студент должен определить разрешённый альтернативный маршрут и защиту от петли. Проверьте отказ отключением только одного транка/линка, не останавливая все серверы; восстановите исходную схему после опыта.

### 4.3. Сравнение с IAX2 (повышенная сложность)

На собственных АТС A и B по желанию настройте дополнительный IAX2-транк с взаимной аутентификацией, отдельным контекстом входящих вызовов и разрешёнными диапазонами. Не переносите старые настройки IAX из исторического пособия без проверки. Сопоставьте IAX2 (обычно UDP/4569, совмещённая сигнализация и медиа) и PJSIP/RTP по портам и структуре трафика. Не заменяйте обязательный PJSIP-транк IAX2.

*Пример 6 — диагностические команды (CLI Asterisk)*

```text
module show like chan_iax2
iax2 show peers
iax2 show channels
```

### 4.4. Абонент за NAT: воспроизведение и устранение неисправности

Создайте дополнительную клиентскую ВМ и учебную ВМ-маршрутизатор с двумя изолированными интерфейсами: внешним в voip-internal и внутренним в отдельной Internal Network voip-nat-lan. Не соединяйте voip-nat-lan с домашней сетью и Интернетом. Клиент размещается в сети маршрутизатора и регистрируется на ast-a через трансляцию адресов; внутренний диапазон выбирайте отличным от 10.77.v.0/24 и Host-Only.

На маршрутизаторе включите IPv4 forwarding и узкое правило SNAT/MASQUERADE только для трафика клиентской подсети к учебной сети Asterisk. Убедитесь, что с клиента есть маршрут к ast-a, что на шлюзе видны трансляции и что доступность не зависит от внешнего Интернета. Для проверок применяйте tcpdump на обеих сторонах NAT.

Воспроизведите проблему под контролем: сравните успешную SIP-сигнализацию с потерей/отсутствием встречного RTP. Сохраните текущие корректные настройки перед изменением; изменяйте по одному параметру, не ломайте доступ SSH и не удаляйте правила маршрутизатора целиком. Исправьте endpoint клиента за NAT настройками rtp_symmetric=yes, force_rport=yes, rewrite_contact=yes и direct_media=no, если признаки диагностики подтверждают их необходимость.

*Пример 7 — параметры endpoint удалённого клиента*

```text
rtp_symmetric=yes
force_rport=yes
rewrite_contact=yes
direct_media=no
```

*Пример 8 — наблюдение трафика и состояния (CLI / Bash)*

```text
pjsip set logger on
rtp set debug on
pjsip show contacts
sudo tcpdump -ni <интерфейс> 'udp port 5060 or udp portrange 10000-20000'
pjsip set logger off
rtp set debug off
```

Команду tcpdump выполните в оболочке Linux, а не внутри CLI Asterisk; обозначение `<интерфейс>` замените действительным именем сетевого интерфейса. Сравните адреса в SDP, адреса/порты источников RTP и наличие ответного аудио после исправления. На стенде без фактически воспроизводимой односторонней слышимости не утверждайте, что она наблюдалась: выполните контролируемую демонстрацию изменения маршрута и объясните ожидаемые последствия.
